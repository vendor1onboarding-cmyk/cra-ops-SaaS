# Time Standardization Audit

Scope: frontend and non-SQL artifacts only (no DB migrations or SQL edits). Focus: inconsistent timestamps between EOD and SOA and other displays.

1) Current database timestamp types (summary from project docs)
- Most production tables use `timestamp with time zone` (`timestamptz`) for event and audit timestamps (e.g., `created_at`, `pickup_time`, `time_in`, `time_out`, `eod_signed_at`). The DB defaults to `now()` for several columns.

2) Current frontend formatting & utilities
- `src/utils/time.ts` — central time utility that:
  - Defines `IST_OFFSET_MS` and manually adds/subtracts the offset in multiple helpers (e.g., `getISTDateString`, `convertUTCToIST`, `convertISTToUTC`).
  - Provides `parseUTCDate()` which normalizes strings and appends `Z` when missing.
  - Provides `formatIST()` and `formatISTFromUTC()` which parse inputs and call `toLocaleString` with `timeZone: 'Asia/Kolkata'`.
  - Also contains `formatISTFromISTEncodedUTC()` for legacy cases where IST was encoded into UTC timestamps.
- Other usages:
  - `src/pages/ATMReplenishment.tsx` defines `toIST(date)` which adds `5.5` hours and returns `toISOString()` (manual offset arithmetic)
  - `src/components/SignatureImage.tsx` sets `timestamp: new Date().toISOString()` when capturing signatures (UTC iso string stored)
  - `src/utils/travelLogService.ts` and `src/pages/TravelTracking.tsx` use `new Date().toISOString()` for logging events.
  - UI display typically uses `formatIST`, `formatISTFromUTC`, or `toLocaleString('en-IN', {timeZone: 'Asia/Kolkata'})` in some components.

3) Inconsistent timestamp locations observed
- `ATMReplenishment.tsx` — `toIST()` adds IST offset manually and returns an ISO string; this creates timestamps that have been shifted and encoded as UTC (IST-encoded-as-UTC), which conflicts with `timestamptz` storage and `formatISTFromUTC` parsing.
- Various places use `new Date().toISOString()` (UTC) when creating event timestamps; other places convert client local time to IST via manual offset then `toISOString()`. This mixed approach produces inconsistent stored instants.

4) Root cause analysis
- Mixed approaches:
  - Some code treats `denom_*` timestamps as true instants and uses `new Date().toISOString()` (UTC) — correct.
  - Other code adds an IST offset to the client-side timestamp and then stores the resulting ISO string (effectively encoding an IST wall-time into a UTC instant). This results in timestamps that when displayed as IST appear shifted by +5:30 (double-shift) or show different values in different views.
- The manual offset arithmetic in `src/utils/time.ts` and ad-hoc `toIST()` functions is brittle and error-prone. Using `toLocaleString` with `timeZone` for display is correct; storing instants should consistently be UTC (timestamptz) without manual offset arithmetic.

5) Recommended centralized IST formatting utility (principles)
- Preserve `timestamptz` in the DB as the canonical instant representation (do NOT change DB timezone or column types).
- Always store timestamps as UTC instants (ISO `Z`) generated by `new Date().toISOString()` or by server-side `now()`.
- Normalize incoming timestamp strings on parse with a single helper that treats timezone-less strings as UTC only if they originate from the server; for client-generated timestamps always send `toISOString()`.
- Centralize display conversion via `src/utils/time.ts` utilities that:
  - Provide `formatIST(date)` which accepts any ISO/timestamptz string or Date and returns localized IST string using Intl with `timeZone: 'Asia/Kolkata'`.
  - Remove any helper that performs manual +5.5h arithmetic when producing ISO strings for storage. Replace `convertISTToUTC` / `convertUTCToIST` with functions that use `Date` and `toLocaleString`/`Intl.DateTimeFormat` for display only.
- Where client needs an IST date-only string for query semantics (e.g., `assignment_date` which is a date in vendor's local day), provide a well-documented helper `getISTDateString()` that computes the local-date in IST by converting `new Date()` to IST using Intl or by using `Date` with timezone-aware libraries. Avoid manual addition of milliseconds; prefer `Intl` or a tested library like `date-fns-tz` or `luxon` for conversions.

6) Files requiring changes (frontend)
- `src/utils/time.ts` — refactor to remove manual offset arithmetic; provide canonical helpers:
  - `toUTCISOString(date?: Date|string): string` — returns ISO Z string (use new Date(date).toISOString()).
  - `formatIST(date)` — existing but ensure it uses `parseUTCDate` correctly.
  - `getISTDateString()` — reimplement using `Intl.DateTimeFormat` with `timeZone` or `date-fns-tz` to get YYYY-MM-DD in IST without manual math.
  - Remove `formatISTFromISTEncodedUTC()` if possible; if needed, document legacy behavior and centralize its use.
- `src/pages/ATMReplenishment.tsx` — remove `toIST()` (manual +5.5h) and use `toUTCISOString()` when storing events; use `formatIST()` for display.
- Any components that generate timestamps by manual offset must be updated: search and replace patterns of `new Date().getTime() + 5.5 * ...` and `toISOString()` combos.
- `src/components/SignatureImage.tsx`, `src/utils/travelLogService.ts`, `src/pages/TravelTracking.tsx` — ensure timestamps are generated via `toUTCISOString()` and displayed via `formatIST()`.

7) Whether DB migration is required
- No database migration should be required if the application standardizes on storing true UTC instants going forward. However, existing records that were saved using incorrect IST-encoded-as-UTC values will remain historically inconsistent; consider a one-time audit/fix script run by DB/analytics team if historical correction is necessary.

8) Backward compatibility risks
- If you retroactively change client-side storage to true UTC, past records encoded with IST-as-UTC will show shifted times when displayed with correct conversion. This is a data-correction risk and must be handled separately (optional migration or accept historical discrepancy).

9) Test cases
- Unit tests for `src/utils/time.ts`:
  - `getISTDateString()` returns correct YYYY-MM-DD for known instants (test vectors around midnight UTC where IST day differs).
  - `formatIST()` converts UTC ISO string to expected localized string (compare canonical outputs).
  - `parseUTCDate()` handles timezone-less, space-separated, and RFC variants correctly.
- Integration tests:
  - Create a sample timestamp with `new Date().toISOString()` and save via API; verify EOD and SOA displays show identical IST-formatted times using `formatIST()`.
  - Simulate legacy IST-encoded-as-UTC strings and verify `formatISTFromISTEncodedUTC()` shows them as previously displayed (for migration planning).

10) Implementation sequence (safe rollout)
- Audit: Add monitoring to detect occurrences of manual offset arithmetic (grep for `+ 5.5 *` etc.).
- Library refactor: Implement `toUTCISOString()` and `formatIST()` canonical helpers in `src/utils/time.ts` (keep existing names as deprecated wrappers for a short window).
- Replace ad-hoc `toIST()` and other manual offset calls with canonical helpers in `ATMReplenishment`, `SignatureImage`, `travelLogService`, and any other files flagged by search.
- QA: Verify EOD and SOA pages show identical IST-formatted timestamps for the same events (using the same record IDs).
- Optional migration: If historical timestamps need correction, plan a server-side remediation script and inform stakeholders.

11) Short summary
- Root cause of inconsistent timestamps: ad-hoc client-side manual timezone arithmetic (adding IST offset) combined with mixed usage of `toISOString()` and localized display methods.
- Fix: standardize on storing UTC instants (`toISOString()`), centralize display using `formatIST()` with `timeZone: 'Asia/Kolkata'`, and remove manual offset math from frontend code. No immediate DB schema migration required.
